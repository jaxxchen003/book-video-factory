# 图书号选题库、自动流水线与可视化运营方案

## 1. 目标与边界

这套工厂下一阶段不应只是“一本书运行一次脚本”，而应成为一个可追踪、可重跑、可比较的内容生产系统：

- 选题先进入统一选题库，不直接创建视频项目。
- 公开趋势信号、微信读书资料、脚本、图片、人声、音乐、时间线、成片和发布后数据保持可追溯关系。
- 自动化负责采集、去重、评分、资料补全、项目初始化、素材生成和技术质检。
- 人工保留四个闸门：选题批准、脚本批准、版权/来源批准、发布批准。
- 所有阶段可重复执行；同一输入与同一版本应得到相同结果，人工批准产物不得被后台任务覆盖。

## 2. 推荐数据架构

采用“SQLite 管状态，仓库目录管大文件”的混合模式。SQLite 适合本地单机、零运维和可视化筛选；视频、音频、图片继续放在现有 `book_video_warehouse/`，数据库只保存路径、哈希、来源和状态。

核心表：

| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `topics` | 选题主表 | `id`、标题、角度、目标人群、状态、总分、负责人 |
| `topic_signals` | 各平台公开信号 | 平台、关键词、指标、采集时间、原始 URL、证据快照 |
| `books` | 候选书与微信读书匹配 | 书名、作者、`book_id`、封面、来源状态 |
| `topic_books` | 一个选题与多本书的关系 | 相关度、主书/备选书、证据说明 |
| `projects` | 已批准选题创建的视频项目 | `project_slug`、模板版本、当前阶段 |
| `pipeline_runs` | 每次流水线运行 | 阶段、输入哈希、状态、开始/结束时间、错误、重试次数 |
| `assets` | 所有素材台账 | 类型、路径、生成模型、提示词、来源、授权、校验和 |
| `publish_jobs` | 发布准备与平台版本 | 平台、画幅、文案、计划时间、审核状态 |
| `performance_snapshots` | 发布后公开数据快照 | 播放、完播、互动、分享、收藏、粉丝转化、采集时间 |
| `experiments` | 钩子/封面/时长/BGM 实验 | 变量、版本、假设、结果、胜出版本 |

选题状态机：

```text
inbox -> enriched -> scored -> shortlisted -> approved
       -> researching -> scripting -> assets -> rendering
       -> qc -> ready -> published -> measured -> archived
```

失败状态不覆盖主状态，而记录在 `pipeline_runs`；修复后从失败阶段重跑，避免整条流水线从头开始。

## 3. 自动运行链路

建议把现有脚本包装成阶段化任务，每个任务都读取上一阶段的 manifest，并输出新的 manifest：

1. `signals.collect`：每天采集公开趋势、榜单和搜索数据。
2. `topics.normalize`：统一关键词、平台、时间窗口和指标口径。
3. `topics.dedupe`：合并同义词、同一事件和重复候选。
4. `topics.score`：按 `config/topic_scoring.json` 评分并保留每项解释。
5. `topics.enrich`：对过线候选调用微信读书，匹配书籍、封面、热门划线和公开点评。
6. `topics.shortlist`：生成每日/每周人工审批队列。
7. `project.create`：选题批准后调用 `init_project.py` 创建仓库项目。
8. `research.collect`：运行 `collect_weread.py`，并保存公开数据证据包。
9. `script.generate`：生成候选钩子、结构和双语脚本，等待人工批准。
10. `assets.generate`：用 GPT Image 生成无字写实画面；真实书封独立合成并记录来源。
11. `voice.generate`：使用锁定 VoxCPM2 音色生成旁白，做响度、静音、爆点和身份一致性 QC。
12. `timeline.render`：运行 V2 渲染器，生成双语版、国际画幅版和 clean master。
13. `qc.run`：校验文件、编码、时长、安全区、字幕、音频、授权和 manifest 完整性。
14. `delivery.prepare`：只有 QC 通过的版本进入交付区；发布仍由人工确认。
15. `performance.collect`：发布后按 2h、24h、72h、7d 保存公开指标快照并回流选题评分。

调度器第一阶段可用 macOS `launchd` 或 cron 每日运行采集与评分；当任务数量变大，再换成带重试和队列的调度器。无论使用什么调度器，任务必须满足：

- 幂等：同一 `topic_id + stage + input_hash + pipeline_version` 不重复生成。
- 可恢复：单阶段失败不影响已批准资产。
- 可观察：每阶段有日志、耗时、错误码和输出 manifest。
- 可版本化：脚本、模型、提示词、字体、音色、BGM 和模板均写入版本号。
- 有磁盘策略：缓存、预览、最终交付分级保留，避免模型和中间视频再次占满磁盘。

## 4. 选题评分模型

基础总分为 100 分，配置文件位于 `config/topic_scoring.json`：

| 维度 | 权重 | 判断方式 |
| --- | ---: | --- |
| 需求强度 | 25 | 搜索量、话题规模、跨平台出现频率 |
| 增长速度 | 20 | 近 24h/7d 增速、视频发布速度、排名上升速度 |
| 互动质量 | 15 | 评论意图、收藏/分享倾向、非灌水讨论比例 |
| 内容缺口 | 15 | 高需求但高质量供给少、头部创作者集中度低 |
| 图书证据 | 15 | 能否找到可靠书籍、划线、章节和观点支撑 |
| 生产适配 | 10 | 是否适合 45–60 秒讲清、能否产生强钩子和写实画面 |

扣分项包括内容过度饱和、版权/来源风险、品牌安全风险和与书籍关系牵强。任何候选至少需要两个独立平台、三条公开趋势证据和两条图书证据，才进入人工 shortlist。

不要只看绝对播放量。更值得优先的信号通常是：

- 关键词搜索和内容发布同时上升，但高质量讲解仍少。
- 评论中频繁出现“哪本书能解释”“怎么做”“有没有方法”等明确需求。
- 收藏/分享意图高于简单点赞，说明内容具有长期价值。
- 多个平台在不同人群中出现同一痛点，而不是单一账号制造的短期峰值。
- 话题可以落到书中明确章节、观点或案例，不需要用书名强行包装热点。

## 5. 可视化管理后台

本地后台建议采用 FastAPI + SQLite 提供 API，前端先做轻量 Web 管理台。首期需要六个页面：

1. **选题雷达**：趋势曲线、证据来源、评分拆解、候选书、风险和“一键进入 shortlist”。
2. **生产看板**：按状态机展示卡片，能查看当前阶段、失败原因、重跑和人工闸门。
3. **项目详情**：从选题证据一路查看到脚本、图片、人声、音乐、时间线、QC 和交付文件。
4. **发布日历**：显示各平台计划、所用版本、标题/文案、审核状态，不直接自动发布。
5. **数据复盘**：展示 2h/24h/72h/7d 表现、钩子留存、完播和互动，并关联到实验变量。
6. **资产与授权**：统一查看封面来源、BGM 授权、字体许可、生成模型、提示词和到期风险。

系统首页只显示需要人处理的事项：待批准选题、待批准脚本、QC 失败、来源风险和待发布成片。这样后台是“生产控制台”，不是文件浏览器。

## 6. 日常维护制度

- 每周：处理 shortlist、复盘过去 7 天数据、淘汰长期低分候选、更新下一周发布日历。
- 每月：检查 VoxCPM2、FFmpeg、字体、GPT Image 接口、微信读书技能和公开数据采集器是否仍可用。
- 每季度：用真实发布表现重新校准评分权重，保留旧权重版本以便回溯。
- 每次模板升级：先用固定回归项目渲染，再比较画面、字幕、响度和文件规格，确认后再设为默认。
- 永久保留：选题证据、批准脚本、最终人声、提示词/模型版本、真实封面来源、授权记录、QC 和最终交付。
- 可清理：可再生成的图片缓存、场景中间片、预览代理和旧 ASR 临时文件；清理必须由 manifest 判断，不能按目录名盲删。

## 7. 推荐实施顺序

### Phase 1：选题库最小闭环

- 建立 SQLite schema、导入/导出 CSV、选题状态机和评分 CLI。
- 允许手工录入公开 URL 与指标，先验证评分逻辑，不急着接所有平台。
- shortlist 批准后自动创建现有仓库项目。

### Phase 2：生产控制台

- 建立选题雷达、生产看板、项目详情和资产授权页。
- 把现有各脚本包装成可重跑阶段，并将运行状态写入 `pipeline_runs`。

### Phase 3：自动采集与调度

- 接入官方 API、公开榜单和合法导出数据。
- 每日自动采集、去重、评分；异常或登录失效时报警，不绕过验证码或平台限制。

### Phase 4：发布后反馈学习

- 导入或采集公开表现快照。
- 建立钩子、主题、时长、画面、BGM 和发布时间实验。
- 用滚动数据校准评分，但保留人工批准和可解释的分项得分。

完成 Phase 1 和 Phase 2 后，这个项目才真正从“脚本集合”升级为可持续维护的视频工厂；Phase 3 和 Phase 4 负责扩大吞吐量和提高选题命中率。

## 8. 公开新媒体数据接入优先级

优先使用官方 API、官方趋势页和官方导出，网页数据只保存公开指标与 URL，不下载或复用他人视频素材。

| 优先级 | 数据源 | 可获得信号 | 接入方式 |
| --- | --- | --- | --- |
| P0 | 抖音开放平台热门视频榜 | 近 24 小时榜单、播放、点赞、评论、热词、热度值 | 申请 `data.external.billboard_hot_video` 权限后调用官方 API |
| P0 | 抖音指数 | 关键词热度、关联内容、人群和趋势 | 登录后的官方工具或合法导出；原巨量算数旧入口按官方迁移说明处理 |
| P0 | YouTube Data API | 关键词新视频、发布时间、播放、点赞、评论、地区热门 | `search.list` 找候选，`videos.list?part=statistics` 批量补指标 |
| P0 | Google Trends | 搜索兴趣、增速、地区、相关查询、实时趋势 | 官方 CSV、Trending Now 导出/RSS，或官方 BigQuery 数据集 |
| P0 | TikTok Creative Center | 地区/行业热门 hashtag、歌曲、创作者和视频 | 官方公开趋势中心，保存排名、帖子量和趋势快照 |
| P1 | Bilibili 综合热门/排行榜 | 中文中长视频主题、标题结构、公开互动 | 官方公开榜单的低频快照与人工抽样 |
| P1 | 小红书开放平台/蒲公英 | 自有投放、合作博主和投后数据 | 仅在账号和 API 权限满足时接入；不把营销 API 当全站趋势 API |
| P2 | 微信指数等登录态工具 | 中文社交热度佐证 | 先人工录入/截图证据；出现稳定官方导出或 API 后再自动化 |

官方入口：

- 抖音热门视频榜：<https://open.douyin.com/platform/resource/docs/openapi/data-open-service/tops-data/hot-video-list/hot-video-list/>
- 抖音指数/巨量算数迁移入口：<https://trendinsight.oceanengine.com/>
- YouTube Data API：<https://developers.google.com/youtube/v3/docs>
- Google Trends：<https://trends.google.com/trends/>
- TikTok Creative Center：<https://ads.tiktok.com/business/creativecenter/inspiration/popular/hashtag/pc/en>
- Bilibili 综合热门：<https://www.bilibili.com/v/popular/all/>
- 小红书开放平台：<https://ad-market.xiaohongshu.com/>

每条公开信号至少保存：`platform`、`metric_name`、`metric_value`、`window_start`、`window_end`、`captured_at`、`source_url`、`region`、`raw_snapshot_path`。不同平台的播放量不能直接相加，应先在各平台、各时间窗口内计算分位数或 z-score，再合成跨平台得分。

推荐派生指标：

- `velocity`：同一关键词或内容在相邻快照之间的增速。
- `engagement_quality`：评论/播放、点赞/播放，以及评论中的问题、求书、求方法、共鸣和反对意图。
- `supply`：时间窗口内相关内容数量和发布速度。
- `creator_concentration`：热度是否主要由少数账号贡献；过度集中要降权。
- `content_gap`：需求分位数减去高质量供给分位数。
- `cross_platform_confirmation`：是否至少在两个独立平台同时出现。
- `book_fit`：能否匹配到可靠图书、章节、划线和可讲述的解决框架。

数据使用原则：Google Trends 的 0–100 是归一化相对兴趣，不是绝对搜索量；YouTube Shorts 的公开 `viewCount` 口径与普通视频不同；抖音官方榜单是近 24 小时离线快照。评分时必须把这些口径写进 `topic_signals.metadata`，不能把不同口径伪装成同一种“热度”。
